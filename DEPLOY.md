# Deploying the Report Automation web app — free, in the cloud

**Recommended host: a Hugging Face Space using the Docker SDK.** Free CPU-basic
tier (~2 vCPU / 16 GB RAM), a public HTTPS URL, and deployment is a `git push` —
no VM, no firewall rules, no `iptables`. Your colleagues open a link and sign in;
your laptop can be off.

Everything lives in one `Dockerfile`, and nothing host-specific is baked in, so
the same image later runs unchanged on an always-on VM (see the appendix).

---

## What the free tier means in practice

Three quirks, and how the app already handles each:

| Quirk | What it means | How this app copes |
|---|---|---|
| **Public URL** | A free *private* Space is only reachable by Hugging Face account holders — your colleagues don't have those. So the Space is **public**. | The app's own username + password login is the gate. Nothing is reachable without signing in. |
| **Ephemeral disk** | Everything written to disk is wiped on restart or rebuild. Persistent storage is a paid add-on. | The X session is **regenerated by signing in again** (`webapp/x_login.py`), not read from a file you have to keep. Finished reports are downloaded immediately. |
| **Sleeps after ~48 h idle** | The Space suspends; the next visit wakes it in a few seconds. | A free uptime pinger on `/health` keeps it warm during work hours (step 6). |

The one real consequence: **a restart mid-job kills that job.** The app detects
this on boot and marks it `interrupted` with "Please submit it again", rather
than leaving it stuck at "running".

## Before you start

**Create a dedicated X account for capturing.** Not your personal one — bulk
captures can get an account rate-limited or suspended.

On that account:
* note the **@handle**, **password**, and the **email address** it uses — X asks
  for the email when it sees a login from an unfamiliar machine, which a cloud
  server always is;
* **turn 2FA off** if you can. It works with 2FA (set `X_TOTP_SECRET` to the
  authenticator secret), but it is one more thing to break.

You do **not** need to run `save_login.py` for this deployment — the server signs
itself in.

## Step-by-step

### 1. Create the Space

Go to <https://huggingface.co/new-space>:

| Field | Value |
|---|---|
| Space name | e.g. `Twitter-Report` |
| License | your choice |
| SDK | **Docker** → **Blank** template |
| Hardware | **CPU basic** (free) |
| Visibility | **Public** (see the table above) |

### 2. Push the app

The Space is a git repo. From this project folder:

```bash
git remote add space https://huggingface.co/spaces/ganbjhs/Twitter-Report
git add .
git commit -m "deploy"
git push space main
```

If the Space repo already has its own commits, push over them once with
`git push --force space main`.

Hugging Face reads the YAML block at the top of `README.md` (`sdk: docker`,
`app_port: 7860`), builds the image, and starts the container. The first build
takes a few minutes — watch it under the **Logs** tab.

### 3. Set the secrets

Space → **Settings → Variables and secrets** → *New secret*. Never commit these.

**Required — who can use the app:**

| Secret | Example | Notes |
|---|---|---|
| `APP_USERS` | `alice:s3cret,bob:hunter2` | Comma-separated `username:password`. Add one per colleague. |
| `SESSION_SECRET` | a long random string | `python -c "import secrets;print(secrets.token_urlsafe(48))"` |
| `COOKIE_SECURE` | `1` | Spaces are HTTPS, so turn the secure-cookie flag on. |

**Required — the shared X capture account:**

| Secret | Notes |
|---|---|
| `X_USERNAME` | the @handle, **without** the `@` |
| `X_PASSWORD` | its password |
| `X_EMAIL` | the account's email — X asks for it on unfamiliar logins |
| `X_TOTP_SECRET` | **only** if that account has 2FA on |

**Recommended — fit the free hardware:**

| Secret | Value | Why |
|---|---|---|
| `MAX_CONCURRENT_JOBS` | `1` | One report at a time. |
| `CAPTURE_WORKERS` | `2` | Two browsers ≈ 1.4 GB. The box has 2 vCPU, so more browsers won't go faster. |

Prefer not to store a plaintext app password? Use a bcrypt hash in `APP_USERS` —
it is detected automatically:

```bash
python -c "import bcrypt;print(bcrypt.hashpw(b'mypassword',bcrypt.gensalt()).decode())"
```

Saving secrets restarts the Space.

### 4. Check the X login

Open the Space URL, sign in, then go to **X login status** in the header.

It should say *Signed in* — the server signs in at startup. If not, press
**Sign in to X now** and read the message. The usual causes are a wrong password
or a missing `X_EMAIL`.

### 5. Run a report

Upload a links file, name it, pick Twitter or Influencer, and Generate.

### 6. Keep it awake during work hours

A Space sleeps after ~48 h idle. Point any free uptime pinger (UptimeRobot,
cron-job.org, Better Stack…) at:

```
https://<your-username>-<space-name>.hf.space/health
```

Every 10–15 minutes is plenty. That endpoint needs no login and does no work.

## Running it

| Task | How |
|---|---|
| Update the app | `git push space main` — HF rebuilds automatically |
| Watch logs | Space → **Logs** tab |
| Restart | Space → Settings → **Restart this Space** |
| Change a password | Edit `APP_USERS` in Settings (restarts the Space) |
| Rotate the X account | Update `X_USERNAME` / `X_PASSWORD`, then press **Sign in to X now** |

### If captures start hitting login walls

The app notices, throws the stale session away, and signs in again on the next
report. If it keeps happening, open **X login status** — the last sign-in
attempt and its error are shown there. Most often X has flagged the account and
wants a manual sign-in from a browser once.

### Tuning speed vs. memory

Chromium uses roughly 300–700 MB per browser, so total ≈
`MAX_CONCURRENT_JOBS × CAPTURE_WORKERS × 0.7 GB`.

On free CPU-basic (2 vCPU / 16 GB) the limit is **CPU, not RAM**:
`CAPTURE_WORKERS=2` is the sweet spot; 4 will not be meaningfully faster and
makes timeouts more likely.

## Troubleshooting

| Symptom | Fix |
|---|---|
| Build fails on the Playwright image | Check the tag in `Dockerfile` matches `playwright` in `requirements.txt` |
| "Nobody can log in" in the logs | `APP_USERS` is unset or malformed — it must be `user:pass,user2:pass2` |
| Login page loops back to itself | Set `COOKIE_SECURE=1` (Spaces are HTTPS) |
| X login says "X did not show the password field" | Wrong `X_USERNAME`, or X is showing a challenge — set `X_EMAIL` |
| X login says "asks for a 2FA code" | Set `X_TOTP_SECRET`, or turn 2FA off on the capture account |
| Job stuck, then "interrupted" | The Space restarted mid-job. Submit it again. |
| Space is slow to first respond | It was asleep. Set up the keep-alive ping (step 6). |

## Appendix — the same image on an always-on VM

If you later want true always-on with a persistent disk, the identical image
runs on a free **Oracle Cloud "Always Free"** ARM VM (2 OCPU / 12 GB) with the
included `docker-compose.yml`:

```bash
sudo apt update && sudo apt install -y docker.io docker-compose-plugin git
sudo usermod -aG docker $USER && newgrp docker
git clone <your-repo> app && cd app
nano .env                      # same variables as the secrets above
docker compose up -d --build
```

Differences from the Space:

* **the disk persists** — `docker-compose.yml` mounts named volumes over
  `/app/data` and `/app/sessions`, so jobs and the X session survive restarts;
* you must open the port yourself — Oracle images ship with restrictive
  `iptables`, so after adding an ingress rule in the VCN Security List you also
  need, on the VM:
  ```bash
  sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 80 -j ACCEPT
  sudo iptables -I INPUT 6 -m state --state NEW -p tcp --dport 443 -j ACCEPT
  sudo netfilter-persistent save
  ```
* for HTTPS, uncomment the `caddy` service in `docker-compose.yml`, put your
  domain in `Caddyfile`, and remove the `ports:` block from `web`;
* the free ARM shape is often **"out of capacity"** at creation — retry, or pick
  a different availability domain.

Auto sign-in works there too; the `X_*` variables go in `.env` instead of Space
secrets. Ask me for the full Oracle walkthrough if you go that route.

> **Do not** deploy to Vercel or any serverless *function* runtime: short
> timeouts, a read-only filesystem, and no persistent browser make them unusable
> for this workload.
